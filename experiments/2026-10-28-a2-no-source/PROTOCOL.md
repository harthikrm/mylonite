# A2: Muse without source (pre-registered 2026-10-28, before any A2 model call)

**Exploratory, development-only.** Same two author-written targets as the pilot, 5 trials each.
This is not an independent replication and not a held-out result, and nothing here supports a
claim that Muse outperforms any baseline. The pilot at `ecf37d9` is not changed. Its directory is
checked to be unchanged (V5).

## 2. The only change, and what remains in the payload

`payload_audit.json` (generated by `a2_audit.py`) and `test_a2.py` establish four things:

- **Equivalence.** For D2 and D3, the round-1 A2 request is byte-for-byte the pilot's *recorded*
  request with its source block replaced by `Service source: not provided.`. The system message,
  catalog, domains, limits, observation, contract, schema, model, `reasoning_effort` and
  instructions are unchanged.
- **Noninterference.** Four rewrites leave the A2 request byte-identical: showing the corrected
  variant, adding answer words, replacing the code, and rewriting the corrected variant. The same
  rewrites change the source-visible request.
- **Leakage checks on every request, before it is sent.** Every request is checked for:
  - no source block and no line of either variant's source;
  - every identifier shared with either variant's source reaching the model through a permitted
    channel.

  The runtime gate `audit.assert_clean` still runs as well. It treats the buggy source as shown,
  so on its own it cannot detect source leakage under A2.
- **What still reaches the model:**
  - operation and argument names (catalog);
  - the 67-command vocabulary, the same for every target (schema);
  - the contract. For D3, the contract's `status_semantics` lists the errors each operation can
    return, for example `purchase` returns `NotFound`, `Unavailable` and `InsufficientStock`, and
    `publish` returns `InsufficientStock`. These are interface facts that hint at preconditions.
    A2 therefore measures whether **reading code** helps beyond the interface description. It does
    not measure Muse with no semantic information; that would need an A3-style renaming ablation,
    which is not run.
  - From round 2 on, feedback on Muse's own experiments, including the store commands observed
    for each operation. This is the same kind of information M3+ gets by profiling.

## 3. Conditions

- `config.json`:
  - targets, seeds, budget, verification, executor and prices are equal to the pilot's;
  - `A2` equals the pilot's `M4` except `include_source: false`;
  - cap $5, strict: a call is refused when spend plus a $0.25 reserve would exceed it.
- M1, M3+ and source-visible M4 are **not re-run**. The comparison uses the pilot's trials at
  `db1f84f`. The A2 manifest records that every file under `src/`, `fixtures/`, `docker/` and
  `tests/` hashes as in the pilot run (V5); the smoke run confirmed it.
- Same model ID, about one hour after the pilot. Model-side drift cannot be ruled out.

## 4. Predictions and interpretation rules (fixed now)

Predictions (author's, before the run):
- **D2:** A2 verified 5/5, median E₁ ≤ 2.
- **D3:** A2 Success@100 ≥ 4/5. The operation names and the error semantics reveal the lifecycle,
  and the contract names the stock.
- **Hints:** round-1 hints will name commands Muse cannot know, so some hint steps will advance
  rather than match.

D3 rules for item 6:
- **R1, source not needed for M4's D3 result:** A2 Success@100 ≥ 4/5.
- **R2, source needed:** A2 Success@1000 ≤ 1/5, or A2's censored median E₁ ≥ M3+'s (211).
- **R3, partial:** anything else.

Schedule hints: the plan predicted "little effect" (§10). Hits on a hint schedule are reported
against base rates from committed data, not from new runs:
- D3's structure: the first depth-first violation is at schedule 6; 120 of 192 schedules
  violate; under random scheduling, 154 of 500 executions violate
  (`experiments/2026-10-28-d3-fixture/`);
- D2: the first depth-first violation is at schedule 2; 12 of 20 schedules violate
  (`experiments/2026-10-28-tracer/`).

With 5 trials this comparison is expected to be inconclusive. It is reported as counts.

## 5. Validity criteria (`check_validity.py`, written with this protocol)

| ID | Criterion |
|---|---|
| V1 | No source in any request (`a2_audit.check`). `audit.findings` is clean. Recorded calls = logged calls |
| V2 | No `error` status. INCONCLUSIVE ≤ 1% of executions. 0 soundness problems |
| V3 | Every corrected-variant schedule passes, in every verification |
| V4 | Every verified trial replays 20/20 with one hash; corrected mode recorded |
| V5 | `src/`, `fixtures/`, `docker/`, `tests/` hash as in the pilot run. The pilot directory is unchanged since `ecf37d9`. Conditions equal the pilot's except `include_source` and the cap |
| V6 | Spend ≤ $5; 10/10 trials recorded; clean manifest at the run commit |

**Stop the run at once, and report rather than patch,** on any of:
- a payload refusal or a cap refusal;
- a soundness problem or a corrected-variant violation;
- repeated executor failures (as in the pilot's §8.C).

If any criterion fails, the run does not count. It is reported, and the owner decides whether
to re-run.

## 6. Analyses planned (no further model calls or method runs)

1. **Comparison.** For A2, M4, M1 and M3+ on each target:
   - verified count, E₁, Success@100/300/1,000 with Wilson 95% intervals;
   - median method seconds, dollars, model calls, rounds to the hit.
2. **Source dependence.** For each A2 trial:
   - hypothesis kind and whether code references were given;
   - for D3, whether the experiment carries the three-step precondition and quantities that
     together exceed the stock;
   - the round and experiment that hit, and the schedule index of the hit;
   - hint adherence (followed, advanced, skipped).

   Each is compared with the pilot's M4.
3. **M3+ argument-blindness.**
   - Derive, from `methods.pair_priority` and the D3 domains, the chance that M3+'s prioritized
     `purchase ∥ purchase` pair cannot violate.
   - Propose an argument-aware variant under a **new method ID, `M3+arg`**, disclosed as
     post-pilot development. `M3+` itself is not changed.
   - Estimate `M3+arg`'s E₁ by replaying M3+'s planning logic over the pilot's **recorded**
     profiles and schedule counts. No executions.
   - The emulator must first reproduce the pilot's M3+ E₁ for all 5 seeds exactly with the
     original priority, or its estimates are not reported. `M3+arg` is not run.
